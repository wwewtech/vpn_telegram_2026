# Как помочь проекту

Спасибо за интерес к каталогу VPN-ботов для России! Здесь — всё, что нужно знать перед первым Pull Request.

## Как устроен репозиторий

- [`data/bots.json`](data/bots.json) — единственный источник данных. Список поддерживается **строго по алфавиту** — сортировку выполняет скрипт, вручную порядок поддерживать не нужно.
- [`schema/bots.schema.json`](schema/bots.schema.json) — формальный контракт данных (JSON Schema, draft 2020-12). Новое поле сначала добавляется в схему, затем в код: `npm run validate` проверяет данные и против схемы, и против инвариантов.
- [`README.md`](README.md) — таблица ботов между маркерами `<!-- BOTS:START -->` и `<!-- BOTS:END -->` **генерируется** из `data/bots.json` в алфавитном порядке.
- `README_EN.md` — английская версия: таблицы не содержит, но её бейдж `updated-YYYY.MM` и метки вида «200+ bots» синхронизируются генератором автоматически.
- `scripts/lib.mjs` — общие утилиты: чтение данных, сортировка, сериализация.
- `scripts/sort-bots.mjs` — сортирует `data/bots.json` по алфавиту (по хендлу, без учёта регистра).
- `scripts/generate-readme.mjs` — генератор: пересобирает отсортированную таблицу и при изменении данных обновляет бейдж `updated-YYYY.MM`; вместе с ним синхронизирует `README_EN.md`.
- `scripts/validate.mjs` — валидатор инвариантов: формат записей, дубликаты (хендлы Telegram нечувствительны к регистру), сортировка и отсутствие ссылок с параметрами.
- `scripts/validate-schema.mjs` — валидатор контракта: `data/bots.json` против `schema/bots.schema.json` (zero-deps профиль JSON Schema).
- `tests/` — юнит-тесты общих утилит и валидатора схемы на `node --test`; CI считает покрытие и публикует бейдж в ветку `coverage`.
- `scripts/check-links.mjs` — еженедельная проверка живости `t.me`-ссылок (`npm run check-links`). Возвращает exit 1, если найдены мёртвые боты (отчёт при этом уже записан); `--no-fail` всегда возвращает 0.
- `.github/workflows/linkcheck.yml` — weekly + ручной запуск: открывает или обновляет Issue со списком подозрительных ботов.
- `.github/workflows/validate.yml` — CI: на каждый push и PR прогоняет тесты, проверяет данные, сортировку и актуальность README.
- `.github/workflows/autofix.yml` — автофикс: сортирует и перегенерирует файлы, затем коммитит результат в PR (для веток этого репозитория) или в `main`.

> **Важно:** не редактируйте таблицу в README вручную — при следующем запуске генератора правки будут перезаписаны.

## Добавить бота

Два равнозначных пути — можно любой.

### Путь 1: Issue (быстрее, ничего локально запускать не нужно)

Откройте Issue по шаблону «Новый бот» (метка `new-bot`), укажите хендл, протоколы, оплату и дату проверки. Мейнтейнер проверит бота на живость и добавит его в каталог.

### Путь 2: Pull Request (полный контроль над правкой)

1. Убедитесь, что бота ещё нет в списке (`Ctrl+F` по `data/bots.json`).
2. Добавьте запись в любое место массива — порядок будет приведён к алфавитному автоматически:

   ```json
   { "handle": "example_vpn_bot" }
   ```

3. Отсортируйте список, перегенерируйте README и проверьте данные (нужен Node.js 20+, зависимостей нет):

   ```bash
   npm run fix        # сортировка data/bots.json + пересборка README.md
   npm run validate   # проверки формата, дублей, сортировки и ссылок
   ```

4. Откройте PR по шаблону: укажите протокол, способ оплаты и дату проверки бота.

## Дата проверки (verified)

Когда бот проверен, у записи появляется месяц проверки:

```json
{ "handle": "AbdalV2rayBot", "verified": "2026-10" }
```

Проставляется **автоматически**: еженедельный `linkcheck.yml` помечает всех живых ботов (`--stamp-verified`), у мёртвых — снимает. В README появляется колонка «Проверено» (у непроверенных — «—»). Вручную можно добавить/обновить при личной проверке бота; формат — строго `YYYY-MM`.

> Verified — это «ссылка открывалась в этом месяце», а не «сервис качественный»: содержимое бота каталог не проверяет.

## Месячные релизы

1-го числа workflow `release.yml` создаёт тег `vYYYY.MM` и GitHub Release с changelog: число ботов, разница с прошлым релизом, коммиты и **реестр живости** (еженедельные наблюдения + погибшие). Это индексируемая страница и повод рассказать о каталоге. Вручную — запустить workflow (Actions → Release → Run).

## Реестр живости (liveness)

Каждый еженедельный прогон linkcheck сохраняет снапшот статусов всех ботов в `data/liveness/YYYY-MM-DD.json`. Снапшоты копятся сами и образуют историю наблюдений: выживаемость по неделям, дата смерти каждого погибшего бота («реестр погибших»), первые появления.

- Посмотреть статистику: `npm run liveness` (или `node scripts/liveness-stats.mjs --markdown` для таблицы).
- Снапшоты пишет только linkcheck — руками их не создавать и не редактировать; контракт — [`schema/liveness.schema.json`](schema/liveness.schema.json).
- Повторный прогон в тот же день не перезаписывает снапшот (идемпотентность в течение дня).

## Проверка живости ссылок

Каждую неделю (плюс запуск вручную) workflow `linkcheck.yml` обходит все `t.me`-ссылки.
Перед стартом выполняется самопроверка метода («канарейка») на двух заведомо известных страницах — живой (@BotFather) и несуществующей:
если t.me сменит разметку и метод перестанет их различать, проверка завершится ошибкой метода,
а не молчаливым «все живы». У живого бота `og:title` страницы содержит его имя, у удалённого — заглушку «Telegram: Contact @…».
Живые боты автоматически получают `verified: YYYY-MM`, мёртвые теряют его; изменения коммитятся в main.
Подозрительные боты попадают в Issue «Автопроверка: возможно нерабочие боты» (метка `broken`).
Вручную: `npm run check-links` (проверка) или `npm run check-links:verified` (проверка + простановка verified). Опция `--out link-report.md` запишет отчёт в файл.

## Сообщить о нерабочем боте

- Быстрее всего — Issue по шаблону «Нерабочий бот» (метка `broken`).
- Ещё быстрее — сразу Pull Request: удалите запись из `data/bots.json` и выполните `npm run fix`. Таблица, нумерация и порядок пересоберутся автоматически, массовых правок в диффе не будет.

## Правила

- **Только боты.** Каталог принимает исключительно ботов (сущности, которым можно написать в личку). Каналы и группы отклоняются: автопроверка определяет тип сущности по разметке t.me (`tgme_page_extra`: у бота — `@handle`, у канала — «N subscribers», у группы — «N members») и помечает их в отчёте как «не боты». Если вы владелец канала — создайте бота и подавайте его.
- **VPN и прокси, которые реально выдают доступ**: VLESS/Reality, WireGuard, Shadowsocks, Outline, MTProto/socks5. Прочие сервисы — только по согласованию в PR (каталог тематический).
- **Ссылки — только вида `https://t.me/<handle>`**, без реферальных, UTM- и `?start=`-параметров. Генератор собирает ссылки только из хендла, а CI отклонит любые параметры, найденные в README.
- **Без дубликатов.** Telegram-хендлы нечувствительны к регистру: `@FooBot` и `@foobot` — один и тот же бот.
- **Строго по алфавиту.** Не расставляйте ботов «по рейтингу» и не переносите их вручную — порядок всегда пересобирает сортировка.
- Хендл: 5–32 символа, `A-Z`, `a-z`, `0–9`, `_`.

## Локальная проверка

```bash
npm run fix        # отсортировать data/bots.json и пересобрать README.md
npm run sort       # только сортировка data/bots.json
npm run generate   # только пересборка таблицы в README.md
npm run check      # проверить всё без записи (валидация + актуальность README)
npm test           # юнит-тесты скриптов (node --test)
npm run check-links # проверить живость t.me-ссылок (weekly в CI, см. ниже)
```

CI (`validate.yml`) прогоняет юнит-тесты и те же проверки: если список не отсортирован, README не пересобран или в ссылках есть параметры — PR не пройдёт проверку. Для PR из веток этого репозитория автофикс (`autofix.yml`) выправит файлы и закоммитит сам; для PR из форков запустите `npm run fix` у себя.

## Стиль

- Язык README — русский, тон — лаконичный, без маркетингового шума.
- Порядок ботов всегда алфавитный (по хендлу, без учёта регистра) — его задаёт сортировка, а не ручная расстановка.
- Экшены в workflow зафиксированы по SHA коммита; dependabot сам предлагает обновления.
- Заголовки и навигацию менять можно, но проверяйте, что ссылки-якоря не сломались.
- Node.js: локально достаточно 20+ (см. `engines` в `package.json`); CI и `.nvmrc` используют 24.
